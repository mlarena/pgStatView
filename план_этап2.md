# План Этапа 2: Сбор статистики и снимки

## 1. Цель этапа

Заменить заглушку `StatsCollector` на реальный сбор данных из `pg_stat_statements` по целевым PostgreSQL-серверам. Реализовать сохранение `Snapshot` и `MetricPoint` в мета-БД, retention policy и API для исторических данных.

**Результат этапа:** фоновая служба параллельно опрашивает все активные БД, складывает снимки и метрики в SQLite, старые точки автоматически удаляются, API отдаёт исторические серии для будущих графиков.

**Зависимость:** Этап 1 завершён (мета-БД, CRUD подключений, фоновый цикл-скелет).

## 2. Что меняется в существующем коде

| Компонент | Изменение |
|-----------|-----------|

## 3. SQL-запросы к целевым БД

### 3.1. Полный снимок pg_stat_statements (для Snapshot)

```sql
SELECT
    s.queryid,
    s.query,
    s.calls,
    s.total_exec_time,
    s.mean_exec_time,
    s.min_exec_time,
    s.max_exec_time,
    s.rows,
    s.shared_blks_hit,
    s.shared_blks_read,
    s.temp_blocks,
    COALESCE(u.rolname, '?')          AS username,
    COALESCE(d.datname, '?')          AS dbname
FROM pg_stat_statements s
LEFT JOIN pg_user u ON u.usesysid = s.userid
LEFT JOIN pg_database d ON d.oid = s.dbid
ORDER BY s.total_exec_time DESC;
```

### 3.2. Агрегаты для дельта-метрик (QPS, среднее время за интервал)

```sql
SELECT
    COALESCE(SUM(calls), 0)            AS total_calls,
    COALESCE(SUM(total_exec_time), 0)  AS total_time,
    COUNT(*)                           AS statements_count
FROM pg_stat_statements;
```

Выполняется **дважды**: значения из текущего и предыдущего снимка. Дельта:

```
QPS           = (calls_now − calls_prev) / interval_seconds
avg_exec_time = (time_now − time_prev) / (calls_now − calls_prev)
```

### 3.3. Предварительная проверка окружения (кэш на соединение)

```sql
-- Наличие расширения
SELECT 1 FROM pg_extension WHERE extname = 'pg_stat_statements';

-- Версия сервера
SHOW server_version;

-- Наличие колонки total_plan_time (PG >= 13 + track_planning)
SELECT 1 FROM information_schema.columns
WHERE table_name = 'pg_stat_statements' AND column_name = 'total_plan_time';
```

Колонки, которых нет, **исключаются из SELECT** — коллектор собирает список колонок динамически.

### 3.4. Нормализация текста запроса (для сравнения между серверами)

`queryid` нестабилен между инстансами — сравнение по нормализованному тексту:

```csharp
// PgStatView.Core/QueryNormalizer.cs
// 1. Замена числовых литералов: WHERE id = 42  ->  WHERE id = ?
// 2. Замена строковых литералов: name = 'Bob'  ->  name = ?
// 3. Схлопывание пробелов, приведение к нижнему регистру ключевых слов
// 4. MD5/SHA256 от результата -> QueryHash (string) — ключ сопоставления
```

`MetricPoint` получает новое поле `QueryHash` (string), индексируется.

## 4. Архитектура сбора

```
CollectionBackgroundService (фоновый цикл)
    │  читает ICollectionIntervalService (интервал live)
    │  читает список IsEnabled БД
    ▼
Task.WhenAll(  по одной задаче на каждую БД  )
    │
    ├─ StatsCollector.CollectAsync(MonitoredDatabase db)
    │     ├─ 1. Открыть NpgsqlConnection (свои пул на БД)
    │     ├─ 2. Проверка расширения/колонок (кэш)
    │     ├─ 3. SELECT снимка -> List<StatementStat>
    │     ├─ 4. SELECT агрегатов
    │     ├─ 5. Normalize query -> QueryHash
    │     └─ 6. Вернуть CollectResult (успех/ошибка + данные)
    ▼
SnapshotWriter (PgStatView.Meta)
    ├─ INSERT Snapshot (RawData = JSON всего снимка)
    ├─ INSERT MetricPoint (топ-N запросов + агрегаты-дельты)
    └─ UPDATE MonitoredDatabase.LastCollectStatus
```

**Обработка ошибок:** ошибка одной БД не должна ронять цикл. Ошибка пишется в лог + статус БД, цикл продолжает остальные. Повтор — на следующем интервале.

**Объём MetricPoint:** сохраняем **топ-N** (по умолчанию N=50) запросов по `total_exec_time` за цикл, а не все тысячи. N — из конфига.

## 5. Обновлённая модель данных

### 5.1. Изменения MetricPoint

```csharp
public class MetricPoint
{
    // ... существующие поля (Этап 1)
    public string QueryHash { get; set; }      // SHA256 от нормализованного текста
    public string? MetricKind { get; set; }    // "query" | "db_qps" | "db_avg_time"
}
```

- `MetricKind = "query"` — метрика конкретного запроса (топ-N)
- `MetricKind = "db_qps"` — агрегат по базе (QueryId = 0, QueryText = null)
- `MetricKind = "db_avg_time"` — среднее время запроса по базе за интервал

### 5.2. MonitoredDatabase — новые поля статуса

```csharp
public string? LastCollectStatus { get; set; }    // "ok" | "error" | "unreachable"
public string? LastCollectError { get; set; }     // текст ошибки
public DateTime? LastCollectedAt { get; set; }    // UTC
```

### 5.3. Новые индексы

- `IX_MetricPoint_MonitoredDatabaseId_MetricKind_CapturedAt`
- `IX_MetricPoint_QueryHash`

## 6. API Endpoints

### 6.1. GET `/api/snapshot/{dbId}`

Текущий (последний) снимок БД:

```json
{
  "dbId": "prod-main",
  "capturedAt": "2026-10-23T10:05:00Z",
  "statements": [
    {
      "queryId": 1234567890,
      "query": "SELECT * FROM orders WHERE id = $1",
      "calls": 15000,
      "totalExecTime": 245000.5,
      "meanExecTime": 16.33,
      "rows": 15000,
      "username": "app_user"
    }
  ]
}
```

### 6.2. GET `/api/metrics`

Исторические серии для D3 (формат уже согласован в task.md):

```
GET /api/metrics?dbIds=prod-main,stage-01&metric=mean_exec_time&queryHash=abc...&from=...&to=...
```

- `metric` — `mean_exec_time` | `calls` | `total_exec_time` | `qps`
- `queryHash` — опционально, если нужна конкретная серия

Ответ — готовая модель D3 multi-line:

```json
{
  "series": [
    { "id": "prod-main", "label": "Production", "color": "#e74c3c",
      "points": [ { "time": "...", "value": 45.2 } ] }
  ]
}
```

**Агрегация на сервере:** если период > 24 часов — точки схлопываются в 5-минутные корзины (`AVG` по корзине), чтобы D3 не задыхался.

### 6.3. GET `/api/compare`

```
GET /api/compare?queryHash=abc...&dbIds=prod-main,stage-01
```

Сопоставление одного нормализованного запроса между БД (по `QueryHash`, не по `queryid`).

## 7. Retention policy

### 7.1. Конфиг

```json
"Retention": {
  "MetricPointDays": 30,
  "SnapshotDays": 7,
  "CleanupIntervalHours": 6
}
```

### 7.2. Реализация

`RetentionBackgroundService : BackgroundService`:

- раз в `CleanupIntervalHours` удаляет:
  - `MetricPoint` старше `MetricPointDays`
  - `Snapshot` старше `SnapshotDays` (они тяжёлые — json-слипки)
- батчами по 10000 строк (SQLite не любит огромных DELETE)
- раз в сутки — `VACUUM` файла SQLite (опционально, если размер вырос)
- логирование: сколько строк удалено

## 8. Детальная разбивка задач

### Задача 1. Пакеты и инфраструктура Collector (0.5 часа)

- `PgStatView.Collector`: `Npgsql` (v9.x)
- `ConnectionStringBuilder` — сборка connection string из `MonitoredDatabase`
- `TargetDbInspector` — проверка расширения, версии, колонок (с кэшем на dbId)

**Результат:** можно открыть соединение с целевой БД и определить её возможности.

---

### Задача 2. QueryNormalizer (1 час)

- `PgStatView.Core/QueryNormalizer.cs` — регулярки: числа, строки в кавычках, IN-списки, пробелы
- `Hash(string) -> string` — SHA256 hex
- **Юнит-тесты:** 8–10 кейсов (`WHERE id = 1` vs `= 2` → одинаковый хеш; разные запросы → разные хеши)

**Результат:** детерминированная нормализация, покрытая тестами.

---

### Задача 3. StatsCollector — реальная логика (2 часа)

- `CollectAsync(MonitoredDatabase db, CancellationToken ct) -> CollectResult`
- Динамический SELECT по доступным колонкам
- Маппинг reader → `StatementStat` (модель в Core)
- Таймаут команды (`CommandTimeout = 15`), `Cancellation`
- Обработка: нет расширения / нет прав (ошибка с понятным текстом в статус)

**Результат:** с реальной PostgreSQL 12–17 возвращается снимок или осмысленная ошибка.

---

### Задача 4. SnapshotWriter + дельта-метрики (2 часа)

- `PgStatView.Meta/Services/SnapshotWriter.cs`
- `Snapshot.RawData` = `System.Text.Json` сериализация всего снимка
- Топ-N `MetricPoint` (`MetricKind = "query"`)
- Дельты QPS / avg_time из агрегатов двух последних снимков → `MetricKind = "db_qps"`, `"db_avg_time"`
- Транзакция на одну запись-цикл (SQLite — атомарно целиком)
- Обновление `LastCollectStatus/LastCollectedAt`

**Результат:** за один цикл в БД появляются 1 Snapshot + N+2 MetricPoint.

---

### Задача 5. Доработка CollectionBackgroundService (1 час)

- Обход `IsEnabled` БД, `Task.WhenAll` c ограничением параллельности (SemaphoreSlim, max 5)
- Изоляция ошибок по БД, запись статуса
- Live-перечитывание интервала между итерациями
- Пропуск цикла, если предыдущий ещё идёт (защита от наложения)

**Результат:** устойчивый параллельный сбор без падения цикла на ошибках.

---

### Задача 6. RetentionBackgroundService (1 час)

- Реализация по разделу 7
- Конфиг-секция `Retention` + binding-класс

**Результат:** старые данные удаляются автоматически.

---

### Задача 7. API: snapshot / metrics / compare (2 часа)

- `SnapshotController` — `/api/snapshot/{dbId}`
- `MetricsController` — `/api/metrics` с агрегацией в корзины (SQL `GROUP BY` по `strftime`)
- `CompareController` — `/api/compare` по `QueryHash`
- Все `[Authorize]`

**Результат:** curl-запросы возвращают корректные серии, формат = модель D3.

---

### Задача 8. Миграция и тесты (1.5 часа)

- `dotnet ef migrations add AddCollectionSupport` (новые поля/индексы)
- Тесты: QueryNormalizer, SnapshotWriter (in-memory SQLite), агрегация MetricPoint в корзины, retention-запрос

**Результат:** всё зелёное, миграция применяется к существующей базе.

## 10. Критерии приёмки

- [ ] Коллектор собирает снимок с реальной PostgreSQL (12–17), где установлено `pg_stat_statements`
- [ ] При отсутствии расширения/прав — понятная ошибка в статусе БД, цикл не падает
- [ ] Одна упавшая БД не мешает сбору остальных
- [ ] Snapshot сохраняется как JSON, MetricPoint — топ-N + агрегаты
- [ ] QPS и avg_time считаются как дельты между снимками
- [ ] Нормализация: одинаковые по структуре запросы с разных серверов получают один QueryHash
- [ ] `/api/metrics` возвращает D3-совместимые серии, для длинных периодов — 5-минутные корзины
- [ ] Retention удаляет старые точки по конфигу
- [ ] Смена интервала сбора из UI применяется без перезагрузки
- [ ] Все тесты проходят
