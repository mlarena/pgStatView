# pgStatView — общее описание системы

## Назначение

**pgStatView** — автономный веб-клиент для централизованного мониторинга и визуализации статистики запросов PostgreSQL из расширения `pg_stat_statements`. Система подключается к нескольким базам данных одновременно, собирает метрики в реальном времени, хранит историю и предоставляет интерактивные графики сравнения и визуализацию планов выполнения запросов.

Система решает задачу, которую штатные средства PostgreSQL не закрывают: `pg_stat_statements` даёт срез статистики только на одном сервере и только на момент запроса. pgStatView агрегирует данные с нескольких серверов, накапливает историю и позволяет сравнивать поведение запросов между окружениями (prod / stage / dev).


## Ключевые возможности

| Возможность | Описание |
|-------------|----------|
| **Мультисерверность** | Одновременное подключение к произвольному числу баз PostgreSQL, параллельный сбор статистики |
| **История метрик** | Периодические снимки `pg_stat_statements` сохраняются в собственной мета-БД для построения графиков во времени |
| **Сравнение БД** | Мультилинейные графики D3.js сопоставляют метрики одного запроса или всей базы между серверами |
| **Фильтрация по таблицам** | Поиск запросов, затрагивающих конкретную таблицу, через анализ текста запроса |
| **Визуализация планов** | EXPLAIN в формате JSON с интерактивным деревом через PEV2, включая сравнение планов двух БД |
| **Управление подключениями** | CRUD для целевых БД через веб-интерфейс, строки подключения хранятся в зашифрованном виде |


## Архитектура

Система построена по трёхуровневой схеме с чётким разделением ответственности.

```
┌─────────────────────────────────────────────────────────┐
│                    Браузер (Frontend)                    │
│         ASP.NET Core MVC Views + D3.js + PEV2           │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP / JSON / SignalR
┌──────────────────────────▼──────────────────────────────┐
│                  PgStatView.Web (ASP.NET Core)           │
│   Controllers │ REST API │ SignalR Hub │ Background     │
└──────────┬───────────────────────────────┬──────────────┘
           │                               │
┌──────────▼──────────┐         ┌──────────▼──────────────┐
│   Мета-БД (EF Core) │         │  Целевые БД (Npgsql)    │
│  PostgreSQL/SQLite  │         │  PostgreSQL + pg_stat_   │
│                     │         │  statements             │
│  • MonitoredDatabase│         │                         │
│  • Snapshot         │         │  Параллельный опрос     │
│  • MetricPoint      │         │  через Task.WhenAll     │
└─────────────────────┘         └─────────────────────────┘
```

### Компоненты

**PgStatView.Web** — точка входа. Содержит MVC-контроллеры для страниц, REST API для фронтенда, SignalR-хаб для push-обновлений и фоновую службу сбора статистики.

**PgStatView.Meta** — слой доступа к собственной базе данных. Здесь хранятся строки подключения (зашифрованные), исторические снимки и точки метрик. Использует EF Core с миграциями, что упрощает эволюцию схемы.

**PgStatView.Collector** — слой опроса целевых баз. Работает напрямую через Npgsql, минуя EF Core, поскольку запросы к системным каталогам (`pg_stat_statements`, `pg_class`, `pg_user`) требуют точного контроля над SQL. Каждая целевая БД опрашивается в отдельном соединении, параллельно через `Task.WhenAll`.

**PgStatView.Core** — доменные модели, DTO, интерфейсы сервисов. Не зависит от инфраструктуры.

### Разделение баз данных

Принципиальное архитектурное решение — **две категории баз**:

- **Мета-БД** — собственная база приложения. Хранит конфигурацию и историю. Контролируется полностью, схема管理 через EF Core миграции.
- **Целевые БД** — внешние PostgreSQL-серверы, которые мониторятся. Только чтение системных каталогов, никаких изменений схемы.

Это разделение позволяет приложению быть по-настоящему автономным: оно не требует никаких изменений на мониторируемых серверах, кроме установленного расширения `pg_stat_statements`.


## Поток данных

1. **Фоновая служба** с настраиваемым интервалом (по умолчанию 60 секунд) запускает цикл сбора.
2. Для каждой активной целевой БД **открывается отдельное соединение** из пула Npgsql.
3. Выполняется набор SQL-запросов: топ по времени, топ по вызовам, агрегаты по БД.
4. Результаты сохраняются в мета-БД как `Snapshot` (полный снимок) и `MetricPoint` (отдельные точки для графиков).
5. **REST API** отдаёт фронтенду список БД (`/api/databases`) и исторические серии (`/api/metrics`).
6. **D3.js** строит мультилинейные графики, где каждая линия — отдельная БД с назначенным цветом.
7. **SignalR** (опционально) пушит новые точки в браузер без перезагрузки страницы.


## Ключевые SQL-запросы к целевым БД

Система опирается на четыре группы запросов:

- **Топ по суммарному времени** — `ORDER BY total_exec_time DESC` с join к `pg_user` и `pg_database` для контекста.
- **Топ по частоте** — `ORDER BY calls DESC` с долей вызовов через оконную функцию.
- **Фильтр по таблице** — `WHERE query ILIKE '%table_name%'` с исключением системных каталогов и самого `pg_stat_statements`.
- **Производные метрики** — два снимка агрегатов (`sum(total_exec_time)`, `sum(calls)`) для вычисления QPS и среднего времени за интервал.

Для сравнения между серверами используется нормализованный текст запроса, а не `queryid`, поскольку последний не гарантирует стабильность между разными инстансами PostgreSQL.


## Технологический стек

| Слой | Технология |
|------|-----------|
| Backend | ASP.NET Core MVC (.NET 8) |
| Доступ к мета-БД | EF Core + Npgsql provider |
| Доступ к целевым БД | Npgsql (raw SQL) |
| Frontend графики | D3.js v7 |
| Визуализация планов | PEV2 |
| Real-time | SignalR (опционально) |
| Шифрование секретов | ASP.NET Core Data Protection |
| Контейнеризация | Docker + docker-compose |


## Модель данных мета-БД

Три основные сущности:

- **MonitoredDatabase** — целевой сервер: идентификатор, отображаемое имя, параметры подключения (пароль зашифрован), цвет для графиков, флаг активности.
- **Snapshot** — полный снимок `pg_stat_statements` на момент времени, сериализованный в `jsonb`. Служит для детализации и аудита.
- **MetricPoint** — нормализованная точка метрики (время, queryid, calls, mean_exec_time, rows, текст запроса). Оптимизирована для запросов построения графиков и партиционируется по дате.

Retention policy удаляет точки старше настраиваемого периода (по умолчанию 30 дней), чтобы мета-БД не росла бесконечно.


## Ограничения и допущения

- **EXPLAIN ANALYZE** реально выполняет запрос. На продакшене используется только `EXPLAIN (FORMAT JSON)` без ANALYZE, либо EXPLAIN на репликах.
- **`queryid` нестабилен** между серверами и версиями — сравнение ведётся по нормализованному тексту.
- **Фильтр по таблице** основан на текстовом поиске и может давать ложные срабатывания — имена таблиц валидируются через `pg_class`.
- **Права доступа** к целевым БД требуют `pg_read_all_stats` или членства в `pg_monitor` для чтения статистики всех пользователей.
- **Разные версии PostgreSQL** — колонки вроде `total_plan_time` доступны только при `track_planning = on`; коллектор проверяет наличие колонок перед запросом.


## Целевая аудитория

- **DBA** — сравнение поведения запросов между окружениями, поиск регрессий после деплоя.
- **Разработчики** — анализ медленных запросов, привязанных к конкретным таблицам, просмотр планов.
- **DevOps / SRE** — централизованный обзор здоровья парка PostgreSQL-инстансов, исторические тренды.


## Итог

pgStatView — это специализированный инструмент, который превращает разрозненные срезы `pg_stat_statements` с разных серверов в единую наблюдаемую картину с историей, сравнением и визуализацией планов. Архитектура с отдельной мета-БД обеспечивает автономность и сохранность конфигурации, D3.js даёт гибкость в построении кастомных сравнений, а разделение слоёв доступа (EF Core для метаданных, Npgsql для целевых баз) — корректную работу с системными каталогами PostgreSQL.
