# План Этапа 4: Таблицы и детализация

## 1. Цель этапа

Добавить табличные представления статистики запросов: топ-запросы по БД, фильтрация по имени таблицы, детальная страница конкретного запроса с историей метрик по всем БД, сравнение планов выполнения (EXPLAIN JSON) для двух БД.

**Результат этапа:** пользователь может посмотреть топ-запросы БД, найти запросы по таблице, увидеть историю конкретного запроса на графике (Этап 3) и сравнить планы выполнения двух БД рядом.

**Зависимость:** Этапы 1–3 завершены (есть история, API `/api/metrics`, D3-графики работают).

## 3. SQL: фильтрация по таблице

Проблема: `ILIKE '%table_name%'` в тексте запроса не является точным поиском по таблицам — может совпасть с псевдонимом, алиасом в константе и т.д.

Решение:
1. Получить маппинг `oid → relname` из `pg_class` (только видимые таблицы/представления/последовательности)
2. В тексте запроса искать вхождения `pg_class.relname` (с защитой от частичных совпадений: `FROM table_name`, `JOIN table_name`, `INSERT INTO table_name` и т.д.)
3. Сохранять найденные таблицы в `MetricPoint` в JSON-колонке `Tables` (массив строк)
4. SQLite: `Tables TEXT` с JSON-массивом, индекс по `Tables` (покрывающий)

```sql
-- Получить таблицы из pg_stat_statements
SELECT DISTINCT
    CASE
        WHEN c.relname IS NOT NULL THEN c.oid::text
        ELSE NULL
    END as table_oid
FROM pg_stat_statements s
LEFT JOIN pg_class c ON (
    -- FROM table_name
    s.query ILIKE '% FROM ' || c.relname || '%'
    OR s.query ILIKE '% FROM ' || c.relname || ','
    -- JOIN table_name
    OR s.query ILIKE '% JOIN ' || c.relname || '%'
    -- INSERT INTO table_name
    OR s.query ILIKE '% INTO ' || c.relname || '%'
    -- UPDATE table_name SET
    OR s.query ILIKE '%UPDATE ' || c.relname || '%'
    -- DELETE FROM table_name
    OR s.query ILIKE '%DELETE FROM ' || c.relname || '%'
    -- WHERE alias.table_name (по имени таблицы, не алиаса)
    OR s.query ILIKE '%.' || c.relname || '%'
)
WHERE c.relname IS NOT NULL;
```

Это запрос дорогой, выполняем **один раз при старте** или **раз в сутки**, результат кешируем в памяти.

## 5. API Endpoints

### 5.1. GET `/api/top-queries`

```
GET /api/top-queries?dbId=prod-main&metric=total_exec_time&limit=50
```

Ответ (берём из последнего Snapshot):

```json
{
  "dbId": "prod-main",
  "capturedAt": "2026-10-23T10:05:00Z",
  "statements": [
    {
      "queryHash": "abc...",
      "query": "SELECT * FROM orders WHERE id = $1",
      "calls": 15000,
      "totalExecTime": 245000.5,
      "meanExecTime": 16.33,
      "rows": 15000,
      "tables": ["orders"],
      "username": "app_user"
    }
  ]
}
```

### 5.2. GET `/api/queries/by-table`

```
GET /api/queries/by-table?dbId=prod-main&table=orders
```

По `Tables` JSON-массиву в `MetricPoint`:

```json
{
  "table": "orders",
  "statements": [ ... ]  // топ-50 по total_exec_time
}
```

**Реализация в SQLite:**

```sql
SELECT * FROM MetricPoint
WHERE MonitoredDatabaseId = 'prod-main'
  AND metricKind = 'query'
  AND json_each.value = 'orders'  -- json_each не работает в SQLite 3.38+
```

Для SQLite < 3.38 — используем `LIKE '%"orders"%'` в колонке `Tables`.

### 5.3. GET `/api/compare` (переработанный)

```
GET /api/compare?queryHash=abc...&dbIds=prod-main,stage-01
```

Возвращает одну серию запроса с метками БД:

```json
{
  "queryHash": "abc...",
  "query": "SELECT * FROM orders WHERE id = $1",
  "series": [
    { "id": "prod-main", "label": "Production", "color": "#e74c3c",
      "points": [ { "time": "...", "value": 45.2 } ] },
    { "id": "stage-01", "label": "Staging", "color": "#3498db",
      "points": [ { "time": "...", "value": 12.1 } ] }
  ]
}
```

### 5.4. GET `/api/explain`

```
GET /api/explain?dbId=prod-main&queryHash=abc...
```

Выполняет `EXPLAIN (FORMAT JSON)` для последнего известного текста запроса на целевой БД.

**Важно:** только `EXPLAIN` без `ANALYZE` — без реального выполнения! Таймаут `statement_timeout = 5s`.

Ответ:

```json
{
  "dbId": "prod-main",
  "query": "SELECT * FROM orders WHERE id = $1",
  "plan": {
    "Plan": {
      "Node Type": "Index Scan",
      "Relation Name": "orders",
      "Planning Time": 0.05,
      "Execution Time": 0.12
    },
    "Plan Details": [ ... ]
  }
}
```

## 6. MVC Views

### 6.1. Топ-запросы — `/databases/{id}/queries`

Таблица с колонками:

| Колонка | Сортировка | Формат |
|---------|-----------|--------|
| # | — | порядковый |
| Запрос | — | `pre` с переносом, кнопка «Копировать» |
| Вызовов | ↑↓ | `15,000` |
| Общее время | ↑↓ | `245 с` |
| Среднее время | ↑↓ | `16.3 мс` |
| Строк | ↑↓ | `15,000` |
| Таблицы | — | теги `orders` `users` |
| Истори | — | кнопка «График» |

- Сортировка по клику на заголовок (JS: сортировка таблицы на клиенте)
- Фильтр по тексту (input) — фильтрация на клиенте
- Кнопка «График» → открывает страницу сравнения с этим `queryHash`
- Фильтр по таблице (input) — фильтрация на клиенте, префильтрованный по `Tables`

### 6.2. Фильтр по таблице — `/databases/{id}/queries?table=orders`

То же, но таблица уже выбрана.

### 6.3. Детальная страница запроса — `/queries/{queryHash}`

- Заголовок: текст запроса (с подсветкой синтаксиса — простая замена ключевых слов)
- Таблицы: теги-ссылки (клик → переход к `/databases/{id}/queries?table=...`)
- **График:** мультилинейный D3-компонент (тот же `multi-line.js`), но с одной серией на БД — `queryHash` из параметров URL
- **План выполнения:** кнопка «EXPLAIN» → AJAX-запрос к `/api/explain` → результат в `<pre>` (JSON с форматированием)
- **Сравнение планов:** кнопка «Сравнить с другой БД» → открывает `/explain/compare?queryHash=abc&dbId1=prod&dbId2=stage`

### 6.4. Сравнение планов — `/explain/compare`

Две колонки:

```
┌─────────────────────┐  ┌─────────────────────┐
│  prod-main          │  │  stage-01            │
│  EXPLAIN JSON       │  │  EXPLAIN JSON        │
│  (форматированный)  │  │  (форматированный)   │
└─────────────────────┘  └─────────────────────┘
```

План загружается AJAX при открытии страницы.

## 7. Изменения в сборщике (Backend)

### 7.1. Индексация таблиц в StatsCollector

```csharp
// StatsCollector.CollectAsync
// ... после получения снимка pg_stat_statements
var knownTables = await _tableCache.GetOrFetchAsync(dbId); // кэш на 24ч
foreach (var stmt in statements) {
    stmt.Tables = FindTables(stmt.Query, knownTables);
    // FindTables: ищет вхождения table_name в контексте FROM/JOIN/INTO/UPDATE/DELETE
}
```

`FindTables` — простой поиск по заранее известным именам таблиц (сортировка по длине имени desc, чтобы `orders` не совпал с `order_items` при поиске подстроки).

### 7.2. Сохранение таблиц в MetricPoint

```csharp
var tablesJson = stmt.Tables.Any()
    ? JsonSerializer.Serialize(stmt.Tables)
    : "[]";
```

### 7.3. Кэш таблиц

`ITableCache` — `ConcurrentDictionary<string, List<string>>` с TTL 24 часа. Обновление — раз в сутки.

**Результат:** в MetricPoint для новых точек есть список таблиц. Старые точки — пустой массив.

**Результат:** JSON-план для любого запроса из базы.

## 10. Критерии приёмки

- [ ] Таблицы из `pg_class` кешируются, обновляются раз в сутки
- [ ] `FindTables` корректно определяет таблицы в запросах (FROM, JOIN, INSERT, UPDATE, DELETE)
- [ ] Топ-запросы отображаются в таблице с сортировкой по клику
- [ ] Фильтр по таблице показывает только запросы, затрагивающие эту таблицу
- [ ] Детальная страница запроса: текст, таблицы-теги, график истории, кнопка EXPLAIN
- [ ] EXPLAIN выполняется только с `FORMAT JSON`, без ANALYZE, с таймаутом 5 сек
- [ ] Сравнение планов показывает два JSON-плана рядом
- [ ] Кнопка «График» на странице топ-запросов открывает страницу сравнения с этим запросом
- [ ] Кнопка «Копировать» копирует текст запроса в буфер обмена
- [ ] Все тесты проходят
